# NotesGPT 性能测量报告（W6）

&gt; 日期：2026-11　环境：WSL Ubuntu / JDK 21 / Spring Boot 3 / Vue3 + nginx
&gt; 方法论：先埋点测量，后优化对比；所有结论以数字为准

## 1. 问答链路耗时分解（GET /api/chat/stream）

| 阶段 | 实测耗时 | 占比 | 归属 |
|---|---|---|---|
| 网络建连+请求发送（MODEL REQUEST） | ~1.1s | ~7% | 网络 |
| 服务端首字延迟（TTFT 减去网络段） | ~12s | ~70% | **模型侧** |
| 流式生成（READER REQUEST） | 11~14s | ~85%（与上段重叠计） | **模型侧** |
| 本地检索（top3，chunks 翻倍前后） | 1~15ms | &lt;0.1% | 应用 |

**结论：应用代码是纯管道，Java 侧无优化价值。** 优化方向若继续，在模型选型/流式策略，不在应用代码。

## 2. 应用端点吞吐基线（wrk -t4 -c100 -d30s）

| 端点 | RPS | 平均延迟 | Max |
|---|---|---|---|
| /test/api/hello（纯应用） | **147,848** | 0.78ms | 54.65ms |
| /api/chat/stream（温和参数 -t2 -c4） | 27.87（假数字） | - | - |

**压测假数字案例**：chat 端点 279 个响应平均仅 ~146 字节 = 几乎全是 kimi 限流错误回包，
RPS 实际测的是"被拒绝的速度"。**方法论：外部依赖接口的压测必须查内容侧指标（响应大小/状态码）。**

## 3. JVM 健康度（30s 压测期间）

| 指标 | 数值 | 判定 |
|---|---|---|
| GC 停顿次数（G1） | 112 次 | 频率正常（ young GC 密集） |
| GC 停顿总时长 | 203ms | **健康（占 0.68%）** |
| JFR 采样热点 | __________（一句话：是 JDK/Spring 内部类 还是应用类） | 预期：前者 |

**附带认知：JVM 预热曲线**——冷启动 RPS 5623 → 预热后 55280 → 稳态 ~147k。
**压测必须同进程、等预热，否则数字差 26 倍只是 JIT 没热。**

## 4. 前端传输优化（nginx gzip）

| 文件 | 优化前 | 优化后 | 降幅 |
|---|---|---|---|
| index-*.js | 73.6 KB | 32.9 KB | **-55%** |
| index-*.css | 4.3 KB | 1.8 KB | **-58%** |

配置：`gzip on; gzip_types text/css application/javascript; gzip_min_length 1k;`
测量纪律：DevTools Network + Disable cache，只看 200 响应（304 缓存命中是假象）。

## 6. 总结论（一段话版）

NotesGPT 的延迟 99% 由 LLM 决定，应用侧（检索、转发、框架）合计占比 &lt;1%；
应用端点自身吞吐 14 万 RPS、GC 停顿 &lt;1%、前端传输经 gzip 降 55%。
本次调优的真实收益是**排除了应用侧的嫌疑**——这比"调了什么"更重要。
